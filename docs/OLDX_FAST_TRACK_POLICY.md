## 4. Approvals: reduce interaction without widening access
GREEN: previously authorized reversible source-only work on review branch, static inspection, relevant local/emulator tests with synthetic data, docs, prompt preparation. No repeat permission. New live read-only cloud calls still require applicable existing precise consent; not automatically GREEN.
AMBER: new exact bounded staging operation/reads, resource creation or changes, synthetic data, scoped deployment, image upload, identity changes, rollback/cleanup. Ask once for the entire explicitly described finite batch (target account/project/region/resource/digest, actions and order, allowed data, limits/time, costs where material, cleanup and rollback, STOP conditions). Only include operations whose target and safeguards are ready; separately required approval remains separate until owner expressly changes it. If already approved and not consumed, execute within that scope without asking again. New scope, expiry, changed resource/digest, unknown prior write or new material risk requires new consent. A generic continue is not approval for sensitive actions.
RED: production release, broad IAM, real user data, Firebase Rules, destructive shared resource operations, ownership or billing changes, secrets, irreversible actions. Require explicit action-specific authority and verified prerequisites. No default public ingress, broad OAuth, long-lived SA keys, weakening tests or cross-owner access.
Owner preference is speed and no unnecessary cost formality/hard cap; still disclose material new spend, existing applicable limits, and provider charging exposure once at relevant consent, no routine billing rechecks. Budget alerts are not hard caps. Risk acceptance is scoped; existing residual-CVE exception is not a technical PASS or universal enabled/production permission.

## 5. Batch template (prepare before operator is involved)
Goal / current verified evidence / exact targets and inputs / required consent reference / preflight / execution / bounded verification / safe cleanup or rollback / final status and evidence. Prefer one reviewed script with sequential internal checkpoints and fail-closed conditions, not a chain of chats. Validate syntax, platform, paths, APIs/CLI flags, expected response shapes (e.g. omitted protobuf false, 403 vs 404), line endings, fixture scope, and possible failure states before sending. Use synthetic local tests/fakes for guard logic if warranted; not proof of cloud acceptance. Verify pinned source hash before sensitive execution. Bound timeouts, output, request counts and resource scopes. Keep read-only preflight before writes; capture operation IDs and write outcomes without leaking secrets. Do not auto-retry writes on ambiguous responses. If async provider operation, poll or use an independent bounded readback when authorized; if separate verification is genuinely necessary do it once. Rollback only if authorized, safe and preimage/no-drift guards match. Never reset consumed markers or silently replay one-shots; no automatic cleanup of shared/unknown dependencies.
Report machine-readable, sanitized RESULT=PASS / PASS_WITH_LIMITS / STOP; REASON; WRITE_ATTEMPTED; RESOURCE_STATE; EVIDENCE (safe reference); NEXT. Preserve private raw evidence on operator machine, only redacted facts/hash/commit/receipt to GitHub.

## 7. STOP and blocker handling
1. Identify exact stage, whether a write happened, error category and existing safe evidence. Do not retry blind or ask user to repeat old output.
2. Diagnose offline from existing log, source or provider documentation; distinguish confirmed from plausible. Fix only the failing dependency; prepare a new scoped recovery if required, retaining old receipts and markers.
3. After one failed approach and one well-founded recovery, reassess alternative supported paths instead of creating endless wrappers. If the problem needs more diagnosis, explain why and target only missing evidence. Prefer a known working tool/artifact, isolation or authorized compensating control. Escalate to owner only for material choice/approval.
4. If external fix/availability blocks a branch, continue independent authorized P0 work. Defer non-launch-blocking chores with exact follow-up and owner-approved risk boundaries where required. Do not wait indefinitely; do not waive mandatory data, privacy, authorization, cleanup or production gates.
5. On unknown provider write, prioritize safe reconciliation/containment; no broad delete, new grant, auto-retry or bypass. Retain unaffected old resources if dependencies unknown and they do not block new work. Verify before claiming removal.
